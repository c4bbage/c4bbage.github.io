![Qwen3.8-27B 接入 DFlash2 草稿实测](/images/posts/2026-08-21-qwen38-nvfp4-dflash2-dgx-spark/cover.jpg)

同一个模型，同一个 SGLang，同一台 DGX Spark——只把草稿模型从 MTP 换成 DFlash2。

单流从 20.9 涨到 28.4 tok/s，你实际等到的速度，提高了三成六。接受长度从 2.2 跳到了 4.23，几乎翻倍。

第一反应是不信。草稿头是现成的，权重是同一个 NVFP4，凭什么换个草稿能快这么多？

问对了。答案不在「换个更好的草稿模型」——DFlash2 做的是**把成本结构从一条曲线，换成另一条曲线**。绕开一条老的代价，撞上一条新的代价。这话怎么讲，往下看。

## DFlash2 是什么：一次前向，出整块 token

DFlash2 是个草稿模型，不是独立语言模型。它跑在投机解码服务端，目标模型是 Qwen3.8-27B-NVFP4，它负责生成待验证的 token。

区别在它出 token 的方式。

传统草稿（EAGLE、MTP）是**逐 token 展开**：每往前推一步，就要做一次完整的草稿头前向。草稿越深，前向次数线性增加。

DFlash2 走的是**块扩散**。一次前向，直接吐出一**整块** token，每个位置保留 top-K 个候选。候选只是一堆互不相连的碎片，于是再让一个轻量的 selector 给「候选之间怎么转移」打分，从已验证的锚点出发，走出一条连贯路径。

块尾部最容易烂——越往后越像在猜。DFlash2 用骨干里的 **two-tap 动态卷积**，把块尾部的草稿质量按住，不让它衰减。

一句话记住：**它的吞吐成本不随草稿深度线性增长，只按块算。** 这就是后面所有 +36% 和那段反转的根源。

## 那 DFlash2 和 DFlash 到底差在哪

一个字面答案：**DFlash2 在 DFlash 的骨架上，加了两个结构**。SGLang 那条 PR 的标题就直接写了——"local convolution + candidate selector"。

- **two-tap 动态卷积**（`attention_conv` 和 `mlp_conv`）。注意力块和 MLP 块各挂一个，把局部上下文卷进来。它是「动态」的，卷积核不是写死的，而是逐 token 由 `kernel_projection` 现场生成。作用就是上面那句：按住块尾部的衰减。
- **候选选择器**（`candidate_selector`，带 `predecessor_codebook` 和 `successor_codebook`）。它在前驱、后继两个候选空间之间打分，把碎片候选接成连贯路径。

怎么判断一个 checkpoint 到底是不是 DFlash2？看两个地方就够，**别认名字前缀**：架构名是不是 `DFlash2DraftModel`，`dflash_config` 里有没有 `conv_kernel_size` / `conv_group_size` / `selector_rank` / `selector_top_k` 这四组参数。

这两个结构在中转仓里能直接摸到：张量名 `candidate_selector.hidden_projection.weight`、`layers.{0..4}.attention_conv.base_kernel`，白纸黑字。

这里有个坑专门等你。镜像里一堆 `_v2` 后缀的文件：`dflash_worker_v2.py`、`dflash_info_v2.py`。看着以为「已支持 DFlash2」？

不是。同目录还有 `eagle_worker_v2.py`、`standalone_worker_v2.py`——`_v2` 是 SGLang 的 **worker 代次命名**，不是算法版本号。判据只有 `conv_kernel_size` / `selector_*` 在不在。不在，就算架构名恰好能解析，也会静默跑成 DFlash1，拿到的是老接受长度。

（机制与官方数字的来源：[z-lab/Qwen3.8-27B-DFlash2 模型卡](https://huggingface.co/z-lab/Qwen3.8-27B-DFlash2)（`incoai/...` 的镜像仓）、[Inco AI 的 DFlash2 博客](https://inco.ai/blog/dflash2/)、[z-lab/dflash 论文实现](https://github.com/z-lab/dflash)。DFlash 原论文是 *DFlash: Block Diffusion for Flash Speculative Decoding*，ICML 2026。SGLang 侧是 PR #35371。）

## 我们此前撞上的那堵墙，正好是它的靶子

这台机器值得试，不是冲着 DFlash2 官方数字漂亮，是因为我们自己摸到过那个成本结构。

我们在 GB10（273 GB/s 统一内存，稠密 27B 全激活）上，给 Qwen3.8 做过 EAGLE 的深度实验。把 `--speculative-num-steps` 从 3 加到 6，`--speculative-num-draft-tokens` 从 4 加到 8——

结果代码 prompt 从 23.57 **掉到** 22.30 tok/s。变慢了。

原因当时就写清楚了：**EAGLE 每多一步草稿深度，就多一次完整的草稿头前向，是线性叠加成本。** 草稿越深，前向次数越多，收益被一次一次摊薄，最后变成负数。

DFlash2 的 `block_size: 8`，一次前向出整块 8 个 token，不逐 token 展开。

它恰好绕开这条我们实测出来的线性代价曲线。

> **我的推断**：这不是「换个更好的草稿模型」，是把成本结构从 O(草稿深度) 换成 O(块数)。这句是推断，机制（块扩散不逐 token 展开）来自模型卡，但「因此绕开线性叠加」是我基于自己 EAGLE 负结果推的，不是别人给的结论。

## 低并发大胜：+36% 是真的，还带着双重劣势

同口径对比，并发 1–8，MTP 换 DFlash2：

| 并发 | MTP 聚合 tok/s | DFlash2 | 变化 | MTP 接受长度 | DFlash2 |
|---|---|---|---|---|---|
| 1 | 20.9 | **28.4** | **+36%** | 2.2 | **4.23** |
| 2 | 39.5 | **55.0** | **+39%** | 2.78 | **3.10** |
| 4 | 77.4 | **94.9** | **+23%** | 2.1 | **4.34** |
| 8 | 138.4 | **170.7** | **+23%** | 2.07 | **4.15** |

接受长度从 2.07–2.97 抬到 **4.01–4.34**，翻倍。

翻译成决策：**单流、个位数并发为主的流量，等到的速度直接快两三成，不用调任何别的。**

而且这是在我们带着**双重劣势**跑出来的：KV 池比 MTP 小了 19.6%（草稿池按目标 token 一比一分配槽位），还被迫丢掉了 `--enable-linear-replayssm-spec`（DFlash2 走 ReplaySSM 只对 KDA 模型有效，Qwen3.8 是 GDN，得删）。

带这双层劣势都赢，说明块草稿这条路，在带宽瓶颈机型上、低并发时，成立。

## 官方数字的口径，说清楚再对比

你可能会拿模型卡的「3.6×」跟我们的 +36% 对比，想确认是不是同一个东西。

不是同一个口径。**模型卡的 3.6× 是在单张 H200 + FlashAttention 3 上测的官方吞吐倍数；我们的 +36% 是在 GB10 上同一台机器同一种并发数的实测。** 机型不同、量化不同、吞吐的绝对基准都不同，两边的倍数不能混着横着比。

能确定说的是：不管 H200 官方口径还是我们 GB10 实测，DFlash2 在低并发下都赢 MTP；这台机器上，收益就是那个 +23%～+39%。

> **推断与事实分开**：上面「模型卡 3.6× 是 H200 口径」是事实（模型卡 description 写明 H200 + FlashAttention 3）；「因此不能拿它跟我们的 +36% 直接比」是我的判断。

## 反转发生在 C=16：撞上的是另一面墙

并发 16 和 32，DFlash2 **落后**了：

| 并发 | MTP 聚合 tok/s | DFlash2 | 变化 |
|---|---|---|---|
| 16 | 243.9 | **202.8 / 221.9** | **−17% / −9%** ⚠️ |
| 32 | 385.0 | **302.8** | **−21%** ⚠️ |

C=16 我们跑了两次，202.8 和 221.9，噪声约 ±9%，单次差异不当信号。但转向是真实的。

现象很清楚：

| 指标 | C=8 | C=16 |
|---|---|---|
| TTFT | 438 ms | **2,000 ms** |
| ITL | 48 ms | **85 ms** |
| 每请求 tok/s | 21.3 | **12.7** |

低并发时块草稿净赚，是因为算力有余量。一到高并发，**块验证每步要验 8 个 token**，batch 内的验证算力开销，比 MTP 的 4 token 直接翻倍。

GB10 是带宽瓶颈机型，我们一直以为会先撞带宽。可这里**先撞的是算力**。

> **我的推断，尚未验证**：高并发的拐点来自块验证算力翻倍，不是带宽。理由是我们文档里「先撞的是算力不是 HBM」的方向一致，且现象（ITL 翻倍、TTFT 拉长）指向验证开销。这只是推断——验证它需要下一步单变量实验。

下一步最值得做的单变量实验：把 `--speculative-num-draft-tokens` 从 8 降到 4 或 6，看拐点能不能右移。块数越少、验证算力越低，拐点越靠后，这个推断就基本坐实。

## 社区里有人看到了更高的数字——我没核实

跟这条实测同时，X 上有用户（@WescheNex1q）发了一个同款配方跑在 Spark 上的结果：C1 34 tok/s、C8 120.58、C32 178.3 tok/s，还带了 GSM8K 67/80、HumanEval 39/40 这类质量分。

**这一条的原始数据我没拿到，无法核实**，而且有几个点跟我们的实测对不上：

- 它的 C1 是 34 tok/s，我们实测 28.4；它自称「200 个真实提示平均 49.5」——同一篇里两个数字差了 45%，高的那个我们复现不出来。
- 质量分用「X/80」「X/40」这类分母，不是 GSM8K / HumanEval 的标准报法，取样口径存疑。
- 我们也没有它的完整 config / 原始日志，图只给到 X 的缩略图。

所以这一节**只作方向参考，不作证据**：它说明「DFlash2 + Qwen3.8-27B + GB10」这个组合社区里确实有人在跑、也在报积极结果；但它给的绝对值，和我们复现的不一致，按纪律我不拿它的数字当结论。

## 这一趟的落点

写代码前我们以为，DFlash2 只是「把草稿头换了个更好的」。跑完才发现，它做的是**把成本结构从一条曲线换成另一条曲线**——绕开了 EAGLE 的线性叠加，却落进了另一片区域的算力墙。

你不能只说它快。你得知道它快在哪一段并发，慢在哪一段，代价换了什么。它不是「更好的草稿模型」，是「另一种代价分布」。

如果你的流量以单流、个位数并发为主，切过去，那 23%–39% 是真金白银。如果你指望它扛高并发，先去做降档实验，别急着切。

至于那条还没做的降档实验——拐点能不能右移，是这篇文章最后欠着的一个问题。

拐点右移了，结论就是「调参即可用的通用件」；不移，它就是「低并发专用件」。这个答案，等下一轮实验。
