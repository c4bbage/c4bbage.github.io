七天里，npm 生态挨了两次性质完全相反的打击。

**7 月 28 日**，Socket 披露一个针对阿里系开发者的定向投毒集群：18 个包，92 天无人发现，终点是一个跨平台 RAT。

**8 月 4 日**，`keyv`（周下载约 1.27 亿）及 `cacheable` 命名空间被投毒，蠕虫在数小时内自我复制到数百上千个包。Socket 在恶意版本发布后约 6 分钟就标记了它——但已经来不及。

一个慢到没人察觉，一个快到来不及反应。把它们放在一起看，会得到一个比任何单独复盘都有用的东西：

> **攻击者的对抗预算分布，是防御措施普及度的负片。**
> 他们肯花钱绕过的，说明你已经部署了；他们懒得绕的，说明没人部署。

这篇文章按这个逻辑走：先看两起事件各自的钱花在哪，再反推你的防御该怎么排序。文末有合并的 60 秒自查。

> **关于数字的说明**：keyv 事件仍在进行中，各家统计口径差异很大（详见文末「一次事件，八种口径」）。查自己是否中招请以**包名 + 版本 + 哈希**为准，不要用规模数字估算风险。阿里那起事件 Socket 未披露下载量与实际受影响范围。所以下文谈的是*手法的有效性*，不是伤害的规模。

# 第一部分 · 定向：92 天的四笔对抗支出

| | |
|---|---|
| **92 天** | 未被发现（4/28 投放 → 7/28 披露） |
| **18 个包** | 组成一条链，单看每个都无害 |
| **3 年** | 前发布的休眠包，今年 3 月底突然连发 3 版 |

2026 年 3 月底，一个发布于三年前、只有一个无害版本的 npm 包 `lib-mtop` 连续推送了三个新版本——典型的账号接管信号。4 月 27 日两个测试包试水，4 月 28 日完整集群投放：10 个顶层诱饵包，包名精确模仿阿里内部 `@ali` scope 下的私有库（`aone-cloud-cli`、`lzd-unified-station-sdk`、`def-open-client` 这类名字，只有在阿里体系里待过的人才写得出来）。

中间这 92 天，没有任何一个扫描器叫过。而按 Socket 的说法，披露时整套基础设施**仍然在线**。

大部分解读会在这里开始罗列手法。我想先问一个更有用的问题：**攻击者为了这 92 天，具体多花了多少工程量？又有哪些明显的加固，他压根没做？**

## 支出一：把"恶意"从代码里挪进关系里

顶层 10 个诱饵包只是空壳，真实逻辑被拆到中间层三个包，每个包只做一件在任何语境下都合法的事：

| 层 | 包 | 它做的事 |
|---|---|---|
| 诱饵层 | 10 个 `@ali` 仿冒包 | 只有一份依赖声明。你以为在装内部库，实际解析到公开 registry 上的同名包 |
| 中间层 A | `cloud-config-fetcher` | 从 GitHub 拉 JSON 配置存为 `.cloud-preferences.json`。*——"拉取远程配置"是每个 SDK 都在做的事* |
| 中间层 B | `local-config-parser` | 读本地配置，解析规则表达式并求值。*——"规则引擎求值"也是每个 SDK 都在做的事* |
| **合流** | **A + B** | **远程代码执行。** 恶意代码藏在那份 JSON 的规则里，伪装成一个数学乘法表达式的一部分 |

**它不在任何一个包的代码里，它在两个包的组合里。**

> **方法论后果**：只要你的审计单位是"包"，这条链就永远是干净的。**审计单位必须是依赖树。**单包视角下 A 是配置下载器、B 是规则引擎，各自都写得出合理的 README；只有放进同一张图，"下载 + 执行"这个组合才会浮现。

## 支出二：把 vm 当靶子，不当墙

求值用 Node.js `vm` 模块——给了整件事一层"我们做了隔离"的合理外观。逃逸只用两行：

```javascript
var F = items.constructor.constructor;   // 拿到 Function 构造器
var p = F('return process')();           // 拿到 process
```

拿到 `process` 后，样本准备了**六种**回退路径去够 `require`/`_load`（`process.getBuiltinModule`、`process.mainModule`、从 global 根对象搜索）。六种回退——这是要跨 Node 版本稳定运行的工程投入，不是 PoC。

Node.js 官方文档明确写着 `vm` **不是**安全机制。如果你代码里有"用 vm 跑不可信表达式"的地方，那不是沙箱，是一个带装饰的 `eval`。

## 支出三：三条完全不同的平台分支

Socket 记录的事实是：第三阶段载荷落地后先做 *"initial reconnaissance and platform fingerprinting"*，然后按宿主系统走三条差异极大的路径——

| 平台 | 行为 |
|---|---|
| macOS | 往 `~/.zshrc` 插入后台脚本，并装一个 10 分钟周期的 Launch Agent |
| Windows | **杀掉阿里官方安全应用 Alilang，把它的核心代码 `app.asar` 替换成木马版本** |
| Linux | 下载二进制到 `/tmp`，分离进程执行，**载入内存后立刻从磁盘删除** |

三套完全独立的持久化实现，是实打实的工程成本。

> **以下是我的推断，Socket 未做此归因。** 这种结构对通用自动化沙箱天然免疫：沙箱的做法是"把包扔进去跑一下看它干什么"，而主流自动化分析环境绝大多数是 Linux 容器、没有企业内网上下文、也不存在 Alilang 这类特定客户端。载荷在其中要么走 Linux 分支把文件秒删（拿不到样本），要么因为环境不匹配而没有可观察的恶意行为。
>
> 它不需要检测虚拟化、不需要反调试、不需要任何传统 anti-VM 技巧——**目标越窄，越不需要对抗通用检测**。这是定向攻击自带的一种免费规避，也是我对"92 天"最合理的解释；但要强调，Socket 只陈述了"未被发现 3 个月"这个结果，没有给出原因。

## 支出四：把基础设施寄生到受害者自己的云上

| 用途 | 地址 | 为什么好用 |
|---|---|---|
| 载荷分发 | `aone-cli-next.oss-cn-beijing.aliyuncs.com` | 阿里体系出网白名单里几乎必然有 `*.aliyuncs.com` |
| 反代 C2 | `diamond-cli-znsxphqell.cn-shanghai.fcapp.run` | 阿里云函数计算。**Serverless C2**——域名随机、随开随弃、由受害者的云厂商托管 |
| 流量伪装 | `Origin/Referer: alidocs.dingtalk.com` | 让请求看起来像钉钉文档在说话 |

**这一条推翻了一个常见建议。**"限制开发环境出网、只放行可信域名"在这里完全失效——载荷源、C2、伪装身份全部落在受害企业本来就必须放行的域名空间内。域名白名单在这种打法面前是 fail-open 的。有效的替代不是更长的白名单，而是**目的地与行为的基线**：这台开发机以前从没连过函数计算，现在每 10 分钟连一次 WebSocket——异常的是模式，不是域名。

# 第二部分 · 反演：他没花钱的地方

现在把这四笔支出反过来看。成熟攻击者不做无用功——他只加固那些真正会拦住他的环节。所以对抗投入的分布，反过来就是防御措施普及度的地图：

| ■ 他重金投入的 | □ 他一分钱没花的 |
|---|---|
| 规避静态审计（拆依赖树） | 对抗流量基线（伪装只改了两个 HTTP 头） |
| 规避自动化沙箱（平台分支） | 对抗包元数据考古（休眠三年突然发版，毫不掩饰） |
| 规避取证（用完即删 / 表达式求值） | 对抗 registry 锁源 |
| 规避域名封禁（寄生受害者的云） | 对抗配置文件完整性监控 |
| → 说明这些防御**人人都有**，已是红海 | → 说明这些防御**几乎没人部署**，边际收益最高 |

右边这一栏就是防御路线图。它不是靠"哪个措施听起来更好"排出来的，是靠攻击者用真金白银投票排出来的。

**这个框架马上要接受一次检验**——七天后的 keyv 事件里，攻击者花钱买了一样阿里那批人根本没碰的东西。

# 第三部分 · 蠕虫：签名验证通过，恶意代码照进

8 月 4 日 09:00 UTC 前后，`keyv` 维护者（Jared Wray）的 GitHub 账号被接管。攻击者直接向主分支推送恶意提交，然后**走项目正常的 GitHub Actions 发布流程**切版本。接下来两小时（UTC）：

| 时间 | 事件 |
|---|---|
| 09:02–09:30 | 仓库出现初始提交、bot 署名的 hook 注入、reset/删除、再注入 |
| 09:30–09:32 | 作用域包 `@keyv/*` 陆续发布，tarball 干净、无 hook |
| **09:35:00.763** | **`keyv@6.0.0` 发布，带恶意 `preinstall` 钩子** |
| 09:38 | `@thiennq/docs-viewer@1.6.2` 发布——已在命名空间之外 |
| 10:09–10:14 | `cacheable` 家族爆发，5 分钟内 9 个包 |
| ~11:28 | Datadog 记录的活动窗口结束 |
| — | Socket 在 `keyv` 发布后约 **6 分钟**标记异常 |

6 分钟检出，仍然扩散到了数百个包。**这个事实本身就说明"更快的扫描"不是这类攻击的答案。**

## 载荷：两级 + 一个很聪明的规避

**第一级 `setup.mjs`** — 下载官方 Bun 运行时（v1.3.13，直接从 GitHub releases 拉，**不校验签名或哈希**），用它执行第二级。为什么用 Bun？**这样恶意逻辑不跑在 `node` 进程里**，绕开一大批基于进程名和 Node 行为的监控。顺带做了 Alpine/musl 检测（`ldd --version` + `/etc/os-release`）和三种解压回退。

**第二级 `Math_Symbol.js` / `math_init.js`** — 约 710–728 KB 的 Bun bundle，重度混淆（各家对混淆手法的描述不一致，见文末）。日志标签暴露了它的模块划分：`[collector]` `[dispatcher]` `[provenance]` `[publish]`。运行时用环境变量 `_NODE_RUNTIME_INIT=1` 做执行守卫，并在系统临时目录留下锁文件 `tmp.dpkg_14527.lock`。

## 战利品清单已经变了

以前的窃密木马拿 AWS key 和 SSH key。这次的清单值得逐条看：

- **云与基础设施**：AWS IMDSv2/v1 与 Secrets Manager 多区域枚举、GCP 服务账号、Azure client secret、HashiCorp Vault（遍历全部 KV）、Kubernetes 服务账号令牌
- **发布身份**：npm token（`whoami` 验活）、GitHub PAT / OAuth / App token / Actions OIDC
- **CI/CD**：Jenkins、Argo CD、Harbor
- **加密货币**：Foundry、Solana、Monero 钱包
- **系统**：`/etc/shadow`
- **泛扫描**：约 200 个 glob 模式 + TruffleHog 风格正则
- **← 新增：AI 工具凭证**：**OpenAI、Anthropic / Claude、Cursor、Codex、Gemini**

最后一条是新的。**AI agent 的凭证已经正式进入常规战利品清单。**

## C2 挂在以太坊上

主 C2 是 `npm-cache[.]com`，但真正的设计在这里：载荷通过 `eth_call` 查询以太坊主网上的一个智能合约（`0xE1f2395ee43e45A1556EC6438a88c31B83493103`）来**动态取回 C2 域名列表**，并准备了多个公共 RPC 节点做回退（`eth-mainnet.nodereal.io`、`go.getblock.io`、`eth.llamarpc.com`）。

意味着：**你封不掉它。**没有可以 sinkhole 的域名、没有可以下架的服务器。要换 C2，攻击者发一笔链上交易即可，已投放的载荷全部自动跟随。Datadog 的说法很准确——这让"DNS 基础设施变得无关紧要"。附带一提，IOC 里还有 `pypi-get[.]com` 和 `js-mirror[.]com`，跨生态的意图写在脸上了。

## 然后是这次真正的大事

多家报告都写到了，但谁都没把它做成标题。Socket 的原文，我逐字核过：

> **"keyv@6.0.0 itself shipped with a passing attestation** because the legitimate release workflow built already-trojanized source."

> "A dedicated provenance component **builds DSSE attestation envelopes, requests Fulcio signing certificates, and submits Rekor transparency-log entries**, so republished versions can ship freshly minted, verifiable sigstore provenance."

Datadog 独立给出了同一判断：

> "In a compromised workflow, a valid attestation can faithfully bind a malicious source and an attacker-controlled build to the resulting package."

这是两件独立的事，第二件更重：

1. `keyv@6.0.0` 带着**有效通过**的 provenance attestation 发布——因为源码在合法构建流水线跑起来之前就已经被投毒了
2. 蠕虫**自带一个 provenance 组件**：给它重新发布的每一个包现签一份可验证的 sigstore 证明，走 Fulcio 签名 + Rekor 透明日志 + npm OIDC trusted publishing

**在这次攻击里，验证 provenance 会让恶意包看起来比没签名的正常包更可信。**

Socket 把结论放在文末当一句 lesson：

> "The lesson is that provenance attests build integrity, not source integrity. The npm and sigstore pipeline did exactly what it is designed to do and still produced a signed, verifiable attestation for malware, because the source it built from was already trojanized."

**签名证明的是"这个产物确实由那条流水线构建"，不是"喂给流水线的源码是干净的"。**

## 而且它是主动去猎可信发布的

这是 JFrog 挖到、其他几家都没有的一条，也是整件事最该被记住的细节：

蠕虫会**专门检测自己是不是跑在带 `release-drafter.yml` 工作流的 GitHub Actions 环境里**。一旦命中（JFrog 举的实例是 opensearch-js 相关仓库），它就：

1. 申请一个 audience 为 npm registry 的 **OIDC token**
2. 往包里注入恶意 `optionalDependencies`
3. 借这个**受信任的工作流上下文**生成 Sigstore bundle，产出合法 provenance

也就是说，这不是"顺手也签个名"，而是**把可信发布本身当成攻击目标去打**。攻击者判断：带 provenance 的包能走通更多消费方的准入策略，所以值得专门写一个模块去获得它。

## 回到预算框架：这次他们花钱了

第二部分那个框架，在这里得到了检验。

阿里那批人**没有**在 provenance 上花一分钱。keyv 的攻击者**专门写了一个模块**，还专门去猎带 trusted publishing 的仓库。按框架的逻辑，这说明一件事：

**provenance 校验已经普及到了值得攻击者付费绕过的程度。**

这不是框架的反例，是框架的确证。同一把尺子还告诉你另一件事——他们**依然**没有在流量基线上花钱（C2 域名裸奔在 DNS 里，靠链上换址而不是靠伪装），也**依然**没有对抗配置文件完整性监控。两起事件、两拨人、隔七天，在这两项上的判断完全一致。

## 死人开关

最后一个细节，Socket 挖得最深：载荷把偷到的 GitHub token 和一个 handler 字符串写进 `~/.config/gh-token-monitor/`（权限 600），装一个 macOS LaunchAgent（`com.user.gh-token-monitor`）或 Linux systemd user service（配 `loginctl enable-linger` 保证注销后仍运行），**每 60 秒轮询一次 GitHub API；一旦发现该 token 被吊销（HTTP 4xx），就执行远端下发的那段 handler 字符串，然后自我清除**。内置 24 小时 TTL。

> "No linter, secret scanner, or release tool installs a background service that watches for its own credential to be revoked and then evaluates a remote-supplied string."

**这条对防守方的实际含义是：轮换凭证这个动作本身，就是触发器。** 处置顺序得改——先断网/隔离主机，再吊销 token，不能反过来。

# 第四部分 · 两起事件的交点：agent

这是两案唯一重合的部分，也是最该被拎出来的部分。

## 阿里案：第四阶段在给 AI 工具打补丁

Socket 报告里有一句话，夹在持久化章节中间，几乎所有转载都没把它拎出来：

> Persistence mechanisms include poisoning of AI-tools by patching Python scripts located inside `.skills` directories of a specific set of tools.

被点名的工具是**钉钉、Wukong、Qoder**。Qoder 是阿里 2025 年 8 月发布的 agentic IDE，1.0 的核心卖点就是自定义 agent 团队与 skill 插件体系。`.skills` 目录不是普通配置目录，**它是 AI agent 的能力定义目录**。

注入方式是往这些目录下的 Python 脚本打标记 `# __INJECT_MARKER__`，附带一段用 `subprocess` 拉起 C2 下载的 `script.js` 的代码（Windows 下带 `0x08000000` 即 CREATE_NO_WINDOW，不弹窗）。顺带一提，诱饵包里有一个叫 `test-skill-zip`。

## keyv 案：七天后，同一件事被做到了规模上

keyv 蠕虫除了污染 npm 包，还有第二条传播路径：用偷来的 GitHub 令牌直接往受害者仓库提交，最多打 50 个分支（跳过 dependabot / copilot 分支）。JFrog 与 Datadog 一致确认，每个分支植入的是**五个文件**：

```
.claude/settings.json      ← SessionStart 钩子
.claude/setup.mjs          ← 加载器
.claude/math_init.js       ← 蠕虫载荷本体
.vscode/tasks.json         ← folderOpen 任务，执行 node .claude/setup.mjs
.vscode/setup.mjs          ← 加载器副本
```

注意第三行：**蠕虫的载荷本体就住在 `.claude/` 里。**这不是"顺手改个配置"，是把 agent 的目录当作自己的安装位置。

**效果是：克隆仓库、或者用编辑器打开目录、或者起一个 Claude 会话，加载器就执行——完全不需要 `npm install`。**

伪造的提交痕迹（也是最好用的自查线索）：

| 项 | 值 |
|---|---|
| 提交信息 | `chore: update config` |
| 伪造署名 | `Co-authored-by: claude <claude@users.noreply.github.com>` |
| 常用分支名 | `dependabot/github_actions/format/setup-formatter` |

**冒用 AI agent 的署名，把恶意提交伪装成 agent 的日常自动工作。**注意它用的是 `Co-authored-by` trailer 而不是 author 字段——所以按作者过滤的排查会漏掉，得搜提交信息体（自查脚本里已修正）。

在这篇文章的上一版结尾，我写过一句预测：

> 下一次值得看的，不是又有多少个包被投毒，而是**第一个直接以 skill 文件为投放目标的包**——省掉前三个阶段，一步到位。

七天后发生了。**但要把差距说清楚，否则就是事后套话**：机制对上了（agent 目录即投放载体、跳过安装环节），投放路径没对上——不是恶意包里附带 skill 文件，而是用偷来的令牌直接往仓库里注入。预测的是终局，来的是同一终局的另一条路。

## 为什么 agent 是更好的目标

以下是我的推断，不是报告结论，但每一步都基于 agent 的公开设计：

- **它握着凭证。** 一个能干活的 coding agent，手上有 git 凭证、registry token、云 API key、内部系统会话——它就是为了替你调用这些而存在的。keyv 事件里 AI 凭证进入战利品清单，说明攻击者已经算过这笔账
- **它没有人在环。** autonomous 模式下没人逐条审阅它执行的命令，很多人还开了跳过权限确认的开关
- **它的持久化不需要进程。** skill / settings 是纯文本文件。改一个文件，不需要驻留后台进程、不需要注册启动项——下次唤起 agent，是*用户自己*把恶意逻辑跑起来的。传统 EDR 的进程行为模型对此基本失明
- **它自带横向移动。** agent 的正常工作就是连内部系统、读代码库、调 API。被污染的 agent 做这些事，在任何日志里都是合规操作
- **它的身份可以被冒用。** `Co-authored-by: claude` 这个 trailer，在一个已经习惯了 AI 提交代码的团队里，没人会多看一眼

回头看一眼你自己的机器：`~/.claude/`、`~/.cursor/skills/`、`CLAUDE.md`、`AGENTS.md`、`.vscode/tasks.json`、MCP server 配置——纯文本、可写、会被自动执行、且几乎不在任何人的资产清单上。

# 第五部分 · 按"让哪笔支出作废"排序的防御

| 序 | 措施 | 让攻击者的哪笔投入作废 |
|---|---|---|
| 1 | **私有 scope 强制锁源**——为 `@ali`/`@yourcorp` 在 `.npmrc` 配置强制 registry 路由 | 阿里案整个诱饵层直接归零。一次配置，10 个仿冒包全部失效。**投入产出比最高**，且攻击者完全没有后手 |
| 2 | **审计单位从"包"改成"依赖树"**——关注跨包的能力组合：谁下载 + 谁执行 | 直接对冲阿里案的支出一 |
| 3 | **认清 provenance 的边界**——它证明构建完整性，不证明源码完整性 | keyv 案的核心。**不要把"签名通过"当作放行依据**，尤其当蠕虫会主动去猎 trusted publishing 时 |
| 4 | **把 AI agent 配置纳入资产与完整性监控**——`.skills/`、`.claude/`、`.cursor/`、`CLAUDE.md`、`.vscode/tasks.json`、MCP 配置 | 两案的共同落点。keyv 蠕虫的载荷本体就住在 `.claude/` 里，而这些文件在绝大多数企业的资产清单上**根本不存在** |
| 5 | **依赖更新加冷却期 / 成熟度门槛**——新版本发布后延迟若干天再进构建 | keyv 案里 6 分钟就被检出，但秒级拉新版的流水线一样中招。JFrog 称其 Curation 的 immaturity policy 让客户"完全免疫"，因为所有被劫持的包都在 24 小时内被标记——**时间是这类攻击最有效的解药** |
| 6 | **包元数据考古**——账号创建时间、长期停更后突然发版、单账号短期批量发包 | `lib-mtop` 休眠三年连发三版、keyv 5 分钟内 9 个包——这些信号**完全裸奔** |
| 7 | **审计 npm trusted publisher 与 OIDC 配置**——检查哪些工作流有发布权 | 直接针对 keyv 蠕虫猎取 trusted publishing 的那一步 |
| 8 | **警惕"自动初始化"语义**——安装或 import 即触发网络请求 / 文件落盘 | npm v12 默认禁用安装脚本是平台侧的对应动作，但 import 时触发、以及 keyv 那种 clone 即执行都不受此约束 |
| 9 | **出网做行为基线，不做域名白名单**——目的地首见告警、周期性连接检测、TLS 指纹 | 废掉阿里案的支出四。前提是承认：C2 托管在你自己的云厂商上、或挂在以太坊合约上时，域名维度已没有信息量 |
| 10 | **不要把 `vm` 当安全边界** | 不针对这两次攻击，针对的是你自己的代码别成为下一个入口 |

> ### 一处自我修正
>
> 这篇文章的上一版把 **可信发布（trusted publishing）** 列在「平台侧已经在做的好事」里。keyv 事件证明我当时没说清它的边界：**OIDC trusted publishing 不只是被顺手用了，而是被当成目标主动猎取。**
>
> 它没写错——去掉长期有效的 token 确实降低了 token 泄露风险。但它防的是"token 被偷"，不防"账号 / 工作流上下文本身被控"。账号失陷时，trusted publishing 反而让重新发包更顺滑，而且顺便附赠一份合法 attestation。
>
> 这是本文能被这两起事件改掉的一条判断，留在这里而不是删掉。

## 平台侧的动作

GitHub 公布的措施：npm 高影响力账号在邮箱 / 2FA 变更后 72 小时只读；可信发布去掉长期 token（边界见上）；npm v12 起默认禁用安装脚本；Dependabot 增加冷却期；Actions 防火墙（预览）做异常出站检测。

在更早的 Shai-Hulud 波次中，GitHub 的处置模式是批量下架恶意包 + 作废带写权限和 2FA 绕过的 npm token。**截至本文更新时，尚未见到针对 8 月 4 日这一波的官方声明**，各家报告也均未引用官方响应。

这些措施都是好事，但注意：它们全部作用在**平台能观测到的层面**。这两次攻击的关键环节——依赖树组合、平台分支、agent 目录注入、链上 C2、源码级投毒——平台一个都看不见。

# 附：一次事件，八种口径

keyv 事件在 24 小时内至少有八家发布了独立分析。它们**不是互相抄的**——同一个样本被多拨人独立逆向，哈希、包名、合约地址一致是必然的。真正说明问题的是它们的**分歧**：

**连名字都没统一**：Aikido 叫 `Shai-Hulud`，JFrog / SafeDep / Phoenix 叫 `Mini Shai-Hulud`，Expel 叫 `ChainDrop`。

**规模数字差了一个量级：**

| 来源 | 口径 |
|---|---|
| Aikido | 868 个包 / 1,381 个版本 / 20 亿月装量 |
| JFrog | 400+ 个包 / 1,700+ 个版本 |
| SafeDep | 420 个包名 / 1,684 个中毒版本 / 涉 9 个组织 |
| Datadog | 受影响包合计周下载 1.5 亿+ |
| hackread | 1,280+ 个包，且"每几分钟新增 50–100 个" |

**技术描述也有冲突**：载荷大小 Socket 记 728 KB、JFrog 记 710 KB；混淆手法 Socket 描述为"base91 多态编码、每作用域独立字母表"，JFrog 描述为"由 PBKDF2-HMAC-SHA256 派生的位置相关替换密码"；`file-entry-cache` 版本 Socket 记 `11.1.7`、Aikido 记 `11.1.6`。

**各家的独有贡献：**

| 来源 | 独有的东西 |
|---|---|
| **Socket** | 最深的逆向：死人开关全机制、DSSE/Fulcio/Rekor 链路、分钟级时间线、provenance 悖论的明确表述 |
| **JFrog** | **主动猎取 trusted publishing**（检测 `release-drafter.yml` → 申请 OIDC token → 铸造合法 provenance）、五文件注入清单、`Co-authored-by` trailer 的准确形式 |
| **Wiz** | 以太坊合约 C2 的详细文档、RPC 回退清单、机器指纹→定向投递、溯源到 Mini Shai-Hulud / TeamPCP / antv |
| **Datadog** | 精确到毫秒的时间线、运行时 IOC（锁文件、环境变量守卫）、provenance 的独立佐证 |
| **Aikido** | 最早的规模统计与滚动更新 |

**给读者的实际提示**：这么大的口径差异说明规模数字不可靠。查自己是否中招请以**包名 + 版本 + 哈希**为准，并以 GitHub Advisory / `npm audit` 的结论为准，不要用下载量估算风险。

各家的引用规范普遍不理想——多数只引自家前作，几乎没有交叉引用。这不构成抄袭，但确实让读者难以交叉验证，也是上面那些矛盾数字一直没被收敛的原因。

# 结语

两起事件，七天，性质相反，指向同一件事。

阿里那批人花了大量工程做三套平台分支去躲自动化分析，却对"有人把这批包的发布者和发布时间连起来看一眼"毫无防备。keyv 那批人专门写了模块去铸造 sigstore 签名、还主动去猎带可信发布的仓库，却让 C2 域名裸奔在 DNS 里。**他们都很清楚哪些防御是摆设，哪些是真的**——而且两拨人的判断一致。

这就是这篇文章唯一想留下的方法：**不要按"听起来重不重要"排你的防御清单，按攻击者的花钱记录排。**

至于方向——供应链的终点正在往前移。以前的终点是开发者的机器，现在是开发者的 agent：一个握着全部凭证、自动执行、用纯文本定义行为、可以冒用身份提交代码、且不在任何资产清单上的东西。七天里两起独立事件都打到了它，一次是补丁 `.skills` 里的 Python，一次是把蠕虫本体安进 `.claude/`。

它今天几乎没有防线，就像三年前的 CI/CD 一样。
